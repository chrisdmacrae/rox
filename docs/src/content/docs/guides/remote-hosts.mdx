Pick a host label from `rex hosts list`. Install `rox` on that host's Rex terminal PATH and prepare the runtime you want to use there. The machine you run the command from needs Rex connectivity to that host.

```sh
rox up container --host buildbox
rox up macos -S studio -- my-agent --model example
```

## What happens

1. On your machine, Rox resolves the repository URL and branch from your current checkout.
2. Rex starts a `rox PROJECT` session on the selected host with a **Provision** tab, which runs `rox up` there.
3. The guest is registered as a Rex host. Its private socket exists only on the selected host, so from your own machine you reach the guest through that host's Rex terminals, unless the selected host puts guests on your tailnet. With [tailnet access](../tailnet/) configured on the selected host, your machine also adds the guest to its own Rex hosts by its tailnet name, so `rex -S WORKSPACE` works directly from where you launched. Remove such a guest with `rox down WORKSPACE --host HOST`, which also removes that host entry.
4. When provisioning succeeds, the Provision session closes. If it fails, the tab stays open so you can see why. When the guest is on the tailnet and the Rex app is open on your machine, Rox [opens the guest's own session](#working-in-the-guests-session) in the app. Otherwise it prints `rox shell NAME`. Any command after `--` runs in the guest's own Rex session.

The selected host uses **its own** config, runtime images, project images, and SSH keys. Overrides such as `--config`, `--git-key`, and `--git-known-hosts` are paths on that host. Quote paths that start with `~` so the selected host expands them.

## Launching without a checkout

To launch from a Rex terminal that isn't inside a source checkout, give the repository URL and branch. `--project` sets the project name, which otherwise defaults to the repository name. Without `--repo`, Rox starts a guest with no project on the selected host.

```sh
rox up container --host buildbox --project my-project \
  --repo git@github.com:organization/my-project.git --branch main
rox up container --host buildbox --no-project
```

## Adding a project to a guest on a remote host

`rox add NAME --host LABEL` resolves the project from your checkout and clones it into the guest `NAME` on that host, in its own Provision tab:

```sh
rox add rv-host-3f9a1c2b7d40 --host buildbox
```

## Working in the guest's session

A Rex pane belongs to the server whose session it's in, and a new split or tab runs on that same server. A shell you open into a guest from another session, such as `rox shell` in a tab on your machine, is one pane over SSH: splitting it opens a shell on your machine, not in the guest. To split and open tabs in the guest, work in the guest's own Rex session:

```sh
rox open rv-my-project-3f9a1c2b7d40
```

The Rex app shows one host at a time, and its host picker can't be driven by a command. So when the app isn't on the guest's host yet, `rox open` opens **Switch Host** and waits for you to choose the guest. If the guest isn't in the list, add it first with `rox add-remote-host NAME`. Once the app is on the guest, Rox selects the guest's project session. `rox up` and `rox add` with `--host` do this for you when they finish.

Inside a guest shell, `REX_SESSION` points at the guest's session, so `rex split` and `rex run` there open in that session too.

## Working with guests on other hosts

`rox shell`, `rox forward`, `rox reconnect`, `rox start`, `rox stop`, `rox down` and `rox add` work on any guest you can see with `rox ls --all`, not just the ones this machine launched. When this machine has no record of `NAME`, Rox asks each of your Rex hosts for it, as `rox ls --all` does, and works on the host that has it. Pass `-S HOST` to skip the search.

```sh
rox shell rv-my-project-3f9a1c2b7d40
rox stop rv-my-project-3f9a1c2b7d40 -S mini
```

- **`rox reconnect`, `start`, `stop` and `add`** run on the guest's host and print what it printed. `rox down` also removes this machine's Rex host entry for the guest.
- **`rox shell`** opens in this terminal when the guest is [on the tailnet](../tailnet/). Rox creates an SSH key for this machine under `~/.local/state/rox/remote/`, adds it to the guest through the guest's Rex server, and connects over a tunnel through that server. The guest's Rex server admits only the tailnet members your policy allows, so the key gives you no access you didn't already have. For a guest that isn't on the tailnet, Rox starts `rox shell` in a Rex session on the guest's host instead, and shows that session in the Rex app.
- **`rox forward`** tunnels through the guest's Rex server, so it needs the guest on the tailnet. Without it, run `rox forward` on the guest's host.

The guest's host needs rox 0.9.0 or later for `rox shell` to open from another machine.
