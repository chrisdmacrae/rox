---
title: Reaching guests from other devices
description: Put each guest's Rex server on your tailnet so any of your devices, and the Rex app, can reach it.
---

By default, a guest's Rex server is reachable only on its launcher. Rox forwards it over SSH to a Unix socket such as `/tmp/rox-501/ID/rex.sock`, and a socket path means nothing on another machine. This matters most when you [launch on a remote host](../remote-hosts/): the guest runs on the launcher, but you work from a different device.

With Tailscale configured on the launcher, Rox also puts each guest's Rex server on your tailnet as its own device, named after the workspace. Any of your devices can then reach the guest by its tailnet name, and the machine you launched from can also use the workspace name:

```sh
# On the laptop that ran rox up --host mini, while the guest runs on the Mac mini:
rex -S rv-my-project-3f9a1c2b7d40 ls
# On any other device on your tailnet:
rex -S rv-my-project-3f9a1c2b7d40.tail1234.ts.net ls
```

Rex runs the tailnet node inside the guest's Rex server. Nothing needs to be installed in the guest, and the guest's own network is unchanged.

## Keep guests isolated

A guest on your tailnet is a device on your network. An agent in the guest can read the node's saved identity, so treat the guest as able to do anything your tailnet lets that device do. Give guests a tag, and write ACLs that let you reach the guests but don't let the guests reach anything.

<Steps>

1. **Add the tag and the grant to your tailnet policy.** In the Tailscale admin console, open **Access controls** and add:

   ```json
   {
     "tagOwners": { "tag:rox-guest": ["autogroup:admin"] },
     "grants": [
       { "src": ["autogroup:member"], "dst": ["tag:rox-guest"], "ip": ["*"] }
     ]
   }
   ```

   Add no rule with `tag:rox-guest` as its source, so guests can't open connections to your devices or to each other. If your policy still has the default rule that allows all traffic, guests can reach everything, so replace that rule with the access your own devices need.

2. **Create an auth key.** In **Settings → Keys**, generate an auth key that is **reusable**, **ephemeral**, and tagged `tag:rox-guest`. Pre-approve it if your tailnet requires device approval. Reusable lets one key enroll many guests. Ephemeral makes Tailscale remove a guest's device soon after the guest stops.

3. **Save the key on the launcher.** Run this on the machine that runs the guests, which for local guests is the machine you're on, and paste the key when asked:

   ```sh
   rox config tailscale
   ```

   It saves the key to `~/.config/rox/tailscale-authkey`, readable only by you, and adds this to `~/.config/rox/config.json`:

   ```json
   {
     "tailscale": {
       "auth_key_file": "~/.config/rox/tailscale-authkey",
       "tags": ["tag:rox-guest"]
     }
   }
   ```

   Pass `--tag TAG` to use other tags, and `--control-url URL` for a self-hosted control server. You can also pipe the key in, for example `op read op://… | rox config tailscale`. If `auth_key_file` is already set, Rox writes the new key to that file.

</Steps>

Auth keys expire, after 90 days at most. When one does, launches stop with a message that the key was rejected. Generate a new key and run `rox config tailscale` again.

## What changes

- **Launch.** After the guest's Rex server starts, Rox enrolls it on the tailnet with the key and waits for it to come up and for Tailscale to issue its HTTPS certificate, which takes a few seconds. It prints the tailnet name, for example `Tailnet  rv-my-project-3f9a1c2b7d40.tail1234.ts.net`. Rox sends the key to the guest's Rex server over SSH, on stdin, so it never appears in a process list. Rex uses it only to enroll the device. Enrollment happens before your setup hook and agent runner start.
- **Host entries.** On the launcher, the Rex host lists two addresses, the socket first and the tailnet name second. After `rox up --host`, the machine you launched from also adds the guest to its own Rex hosts at the tailnet name, so `rex -S WORKSPACE` works there too. Each Rex home keeps its own host list, so a host added on one machine only reaches another when both follow the same home. On any other device, use the tailnet name, or add it with `rex hosts add WORKSPACE TAILNET_NAME`.
- **Who can connect.** A tagged guest belongs to its tag, not to you, so Rox lets the tailnet decide who may connect, and the grant above admits your tailnet's members. Without `tags`, the guest belongs to whoever created the key, Rex admits only that person, and the guest gets that person's ACL access. That's why you should use a tag.
- **Rex app.** When `rox up` offers to add the guest to the Rex app, it copies the tailnet name, which works from the app on any device.
- **Dev servers.** From any device, `rex -S WORKSPACE forward open BLOCK` forwards a server running in a guest terminal. `rox forward` still works on the launcher.
- **Reconnect.** `rox reconnect` and `rox add` turn tailnet serving back on if the guest's Rex server restarted, and use the key again if Tailscale removed the ephemeral device.
- **Removal.** `rox down` signs the guest's device out of the tailnet before deleting the guest. For a guest you launched with `--host`, run `rox down WORKSPACE --host LAUNCHER` from the machine you launched from. It removes the guest on the launcher and the host entry on your machine.

Pass `--no-tailscale` to `rox up` to keep a single guest off the tailnet. A project's `.rox.json` can't turn this on or off. Only the launcher's config controls it.

<Aside>
	To use a self-hosted control server such as Headscale, add `"control_url": "https://headscale.example.com"` to the `tailscale` settings.
</Aside>

## Sharing a guest's server on the internet

`rox funnel` puts a server running in a guest on the public internet with [Tailscale Funnel](https://tailscale.com/kb/1223/funnel), for example to show someone a dev server or to receive webhooks:

```sh
rox funnel rv-my-project-3f9a1c2b7d40 5173
# Funneling https://mini.tail1234.ts.net/ to port 5173 on rv-my-project-3f9a1c2b7d40
```

The funnel runs on the guest's launcher, not in the guest. Rox tunnels a port on the launcher to the guest's `localhost` over SSH, so the server can keep listening on `localhost`, and asks the launcher's Tailscale to funnel that port. The public address is the launcher's tailnet name. The guest's own tailnet device is Rex's node, and it can't funnel.

You need:

- **Tailscale installed on the launcher**, signed in to your tailnet. On a Mac, the Tailscale app is enough.
- **Funnel allowed for the launcher** in your tailnet policy. Give your own devices the `funnel` attribute, and not `tag:rox-guest`, so guests can't expose anything themselves:

  ```json
  "nodeAttrs": [
    { "target": ["autogroup:member"], "attr": ["funnel"] }
  ]
  ```

Funnel listens publicly on ports 443, 8443 and 10000, with one hostname per launcher. To funnel several servers, give each its own port or path:

```sh
rox funnel rv-my-project-3f9a1c2b7d40 3000 --https 8443
rox funnel rv-my-project-3f9a1c2b7d40 8080 --path /api
```

Rox won't take an address that another guest, or something else on the launcher, already funnels.

- **List** a guest's funnels with `rox funnel NAME`. `rox ls --json` lists them too.
- **Stop** one with `rox funnel NAME PORT --off`, or all of a guest's funnels with `rox funnel NAME --off`.
- **Restarts.** Funnels come back when the guest does, with `rox start`, `rox reconnect` or the [rox service](../keep-running/). The server in the guest doesn't come back on its own, so start it again after a restart.
- **`rox stop` and `rox down`.** `rox stop` takes a guest's funnels off the internet until `rox start`. `rox down` removes them.
- **Guests on other hosts.** `rox funnel` works on guests on other Rex hosts too. It runs on the guest's launcher, which needs Tailscale.

<Aside type="caution">
	Anyone on the internet can open a funnel. Dev servers usually have no sign-in, and an agent in the guest controls what it serves. Funnel only what you mean to share, and turn it off when you're done.
</Aside>
