Rox can install Claude Code and Codex in every guest it starts, with their credentials ready. A worker started with `rex run -- claude ...` or `rex run -- codex ...` works right away, with no setup hook and no sign-in.
Both agents are installed in every guest by default. Agents you have not set up are installed without credentials, and `rox config agents NAME --off` (or `"agents": {"codex": false}` in the config) leaves one out.


## Set it up

Run `rox config agents` on the launcher, which is the machine that runs the guests. For guests on a [Rex remote host](../remote-hosts/), run it on that host, because guests get their credentials from the config of the machine that runs them.

<Steps>

1. **Claude Code.** Create a long-lived token for your Claude subscription, then save it:

   ```sh
   claude setup-token
   rox config agents claude
   ```

   Paste the token when Rox asks for it. You can paste an Anthropic API key (`sk-ant-api…`) instead, and Rox sets `ANTHROPIC_API_KEY` in place of `CLAUDE_CODE_OAUTH_TOKEN`.

2. **Codex.** Sign in with your ChatGPT account on the launcher, then point Rox at the login:

   ```sh
   codex login
   rox config agents codex
   ```

   Rox copies `~/.codex/auth.json`, or `$CODEX_HOME/auth.json`, into each guest. To use an OpenAI API key instead, run `rox config agents codex --api-key`.

</Steps>

Run `rox config agents` with no agent to choose both interactively. When stdin isn't a terminal, Rox reads the token or key from stdin. Leave the token blank to install an agent without credentials.

Rox saves each token next to the config, readable only by you, and records it in the config's `agents` section:

```json
{
  "agents": {
    "claude": { "token_file": "~/.config/rox/claude-token" },
    "codex": { "auth_file": "~/.codex/auth.json", "version": "0.171.0" }
  }
}
```

Pass `--no-agents` to `rox up` to start one guest without them. `rox config agents claude --off` stops installing Claude Code in new guests and deletes the token Rox saved for it.

## What a guest gets

- **The CLIs** in `~/.local/bin`, installed with each tool's official installer.
- **Claude Code's credential** in `~/.rox/agents.env`, which the guest's Rex server reads when it starts. Every terminal and `rex run` worker it opens gets the credential. Login and interactive shells read the file too. Rox also marks Claude Code's onboarding as done, so a worker doesn't stop at the welcome screen.
- **Codex's login** at `~/.codex/auth.json`, or, with an API key, the result of `codex login --with-api-key` in the guest.

The credentials go to the guest over SSH, on stdin, so they never appear in a command line or a Rex session. They're never written into an image.

<Aside type="caution">
A guest with these credentials can spend on your account, the same way the agent can on your own machine. Guests are isolated and short-lived, but treat each one as able to use your subscription or API key.

Each guest refreshes a copied Codex ChatGPT login on its own. If guests start signing each other out, switch Codex to an API key with `rox config agents codex --api-key`.
</Aside>

## Your skills, instructions and MCP servers

Guests get the skills, instructions and MCP servers that the project's repository holds, such as `.claude/skills/`, `.mcp.json`, `CLAUDE.md` and `AGENTS.md`, because they come with the clone. Rox also copies some of the launcher's own agent setup into each guest when it starts:

| What | Copied | From the launcher |
|---|---|---|
| `skills` | By default | `~/.claude/skills`, `~/.codex/skills` and `~/.agents/skills`. Links are followed. The rox skill is left out, because rox isn't installed in guests |
| `instructions` | By default | `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md` |
| `mcp` | When you turn it on | MCP servers that run over the network: Claude Code's user-scope `http` and `sse` servers in `~/.claude.json`, and Codex's `url` servers in `~/.codex/config.toml` |
| `settings` | When you turn it on | `~/.claude/settings.json` and the rest of `~/.codex/config.toml`, without hooks, the status line, `env`, `notify`, plugins and per-project entries, which name programs and paths on the launcher |

Choose what to copy for each agent with `--sync`, and name MCP servers with `--mcp`:

```sh
rox config agents claude --sync skills,instructions,mcp
rox config agents codex --mcp docs --mcp linear
rox config agents claude --sync none
```

Changing only what's copied keeps the agent's credentials, so Rox doesn't ask for them again. Rox prints what new guests will get. In the config, it's the agent's `sync` object:

```json
{
  "agents": {
    "claude": { "token_file": "~/.config/rox/claude-token",
                "sync": { "skills": true, "instructions": true, "mcp": ["docs"], "settings": false } }
  }
}
```

`mcp` is `false`, `true` for every MCP server that runs over the network, or a list of server names.

Rox records what it copied in the guest's `~/.rox/synced.json`. The next copy replaces it, so a skill you delete on the launcher leaves the guest too, and MCP servers the guest set up itself stay. `rox update-agents NAME` copies the current setup into a running guest.

- **MCP servers that run a program**, such as `npx` or a binary on your Mac, aren't copied, because the guest doesn't have the program. Install them in a [project image](../project-images/) or the project's `.mcp.json` instead.
- **MCP servers that sign in with OAuth** need signing in again inside the guest. The launcher keeps those tokens in its keychain. Headers and API keys written in a server's settings are copied, into files only the guest user can read.
- **Plugins** aren't copied. Neither are skills that come from plugins.
- **For guests on a [Rex remote host](../remote-hosts/)**, the copy comes from that host's setup, not yours.

## Staying on the latest release

By default, each agent follows its latest release. Rox checks for one at `rox up`, at most every six hours, and caches the answer. A failed check never stops a launch: Rox uses the last version it found. Pin a version with `--version`, and go back to the latest with `--version latest`:

```sh
rox config agents codex --version 0.171.0
```

**Containers** get the agents in one last image layer, built on the base or [project image](../project-images/) and named after it with `-agents`, such as `rox:linux-agents`. When a new release comes out, only that layer rebuilds, which takes about half a minute. Your `.rox.sh` doesn't run again. If the layer fails to build, the guest installs the agents when it boots instead.

**Tart VMs** install the agents when they boot, and skip any that are already at the right version. Project images for Tart include them, so later boots only update.

**To start an agent in a running guest**, in a new Rex session at a checkout:

```sh
rox agent NAME --open-shell
rox agent NAME api --agent codex -- "fix the failing tests"
```

**Guests that are already running** keep their versions until you update them:

```sh
rox update-agents NAME
rox update-agents --all
```

`rox update-agents` checks for the latest releases, installs any that a guest lacks, and writes the current credentials again. New shells get changed credentials right away. Workers that `rex run` starts get them after the guest restarts with `rox stop NAME` and `rox start NAME`, because the guest's Rex server reads them when it starts.
